### AI-Powered Multilingual Video Intelligence Platform

### 1\. Project overview

Our platform accepts a video file or a supported video URL and analyses both its audio and visual content.

For example, imagine a one-minute Japanese video containing:

* A person speaking negatively about a medicine.

* Japanese subtitles burned into the video.

* Images displaying product names and medical benefits.

* Chat screenshots containing patient experiences.

* Visual information about symptoms and adverse effects.

Our system should understand all these sources, translate the relevant content into English, identify important entities, compare what is spoken with what is displayed, and generate a complete evidence-backed report.

Our central principle:

The system must not analyse only what the speaker says. It must also understand everything important displayed visually.

### 2\. Overall system architecture

We divide the platform into six major layers.

1\. Frontend layer

React + TypeScript

Upload video, enter URL, click Analyse and view results.

2\. Backend and orchestration

Python + FastAPI

Manage the analysis job and coordinate every processing stage.

3\. Video preprocessing

FFmpeg + OpenCV

Extract audio, frames, timestamps, metadata and subtitle tracks.

4\. AI intelligence layer

Azure OpenAI

GPT-4o + GPT-4o Transcribe

Speech recognition, translation, vision and reasoning

5\. Evidence and storage layer

Azure SQL + Azure Blob Storage

Store original media, extracted assets and structured evidence.

6\. Output layer

Python + React

Transcripts, subtitles, visual insights, summaries, JSON and PDF.

Why two storage systems?

* Blob Storage stores large files such as videos, extracted frames, audio and PDFs. Microsoft Learn +1

* Azure SQL stores structured records such as video IDs, evidence IDs, timestamps, extracted entities and analysis results.

They serve different purposes.

Main intelligence model

Azure OpenAI · East US

Model 2: GPT-4o Transcribe

Speech recognition

Azure OpenAI · intended deployment region: East US

Let's use our Japanese medicine-related video example throughout.

Technology: React + TypeScript + FastAPI + Azure Blob Storage.

What happens:

* User uploads a video or provides a supported URL.

* React sends the video to our FastAPI backend.

* Backend validates the file format, size and duration.

* The original video is stored in Azure Blob Storage.

* Backend generates a unique `video_id` and processing job ID.

Example:

```json
{
  "video_id": "VID_001",
  "filename": "japanese_medicine_video.mp4",
  "language": "ja",
  "status": "uploaded"
}
```

The user clicks Analyse. The backend starts the complete processing workflow.

### Stage 2 — Video preprocessing

![What is a favicon? How does a website icon impact brand recognition and click-through experience?](https://images.openai.com/static-rsc-4/AfhUeLW6dGwsMyGHYSgh6Pg58My1GhF2MXU6fHZUSC_8-NVLKcEp_wjJ7Vw5vuQ48x-JVCQH4nQr9jMuHA9pnPNP97-_OuvVCwyoKkV3w2CppQj2FFACAyAVAH-kvgWLHUZO6gAnkh0EKWk9BRoDCGzu57kQWsW3Wiq6zFySwaeknEHE_ly8uHB7zHMRsNaF?purpose=fullsize)

Technology: Python + FFmpeg + OpenCV.

This stage prepares the video for AI analysis. No GPT calls are required here.

We extract:

| Asset                    | Example output                     |
| ------------------------ | ---------------------------------- |
| Original audio           | original_audio.wav                 |
| Video frames             | frame_001.jpg, frame_002.jpg       |
| Video metadata           | Duration, FPS, resolution          |
| Embedded subtitle tracks | embedded_subtitles.srt, if present |
| Frame timestamps         | 00:00:05.500                       |

For a 60 FPS, one-minute video:

60 \\times 60 = 3,600 \\text{ frames}

We can extract all 3,600 frames locally, but we should not send all of them to GPT-4o.

Instead, we use:

* Scene-change detection.

* Near-duplicate frame removal.

* Text-change detection.

* Important visual-region detection.

* Additional sampling when content changes rapidly.

We preserve the timestamps of all selected frames.

Important distinction: Embedded subtitles are extractable as subtitle tracks. Burned-in subtitles are part of the video image, so they must be read visually.

### Stage 3 — Japanese speech transcription

![Tactiqによるリアルタイムの日本語会議トランスクリプション](https://images.openai.com/static-rsc-4/HGauiLbkirYRZCgv7J9GR5i_MkbJgFY8vaZ_Pt4-vKwxzbjFKQzuWqcMKZF1BFM6Bjkv6kAOF9KOY5MRFdLKGO6S2ry-Rj-d9Jv062tTnMTQoyHZGOXkLdyVtcbvBo7fxRU98hJ_1Ze8-yQPXbV2IxsZnsKyU-K1T4jbMU3m6x-16pwBBSnMQ7H41CwLEQiD?purpose=fullsize)

Model: `gpt-4o-transcribe`.

Input:

`original_audio.wav`

The model processes the Japanese audio and returns a Japanese transcript.

Illustrative result:

```text
00:00:02 - この薬は効果があると言われていました。

00:00:08 - しかし、実際には副作用が報告されています。

00:00:15 - 患者は頭痛や吐き気を経験しています。
```

We retain:

* Original Japanese text.

* Segment start and end times, if supported by the transcription mode.

* Language information.

* Any available confidence or quality metadata.

The transcript becomes the source for translation.

Model: GPT-4o.

Input: Japanese transcript.

GPT-4o translates the transcript into English while preserving the original meaning.

Illustrative result:

```text
00:00:02
This medicine was said to be effective.

00:00:08
However, adverse effects have been reported in practice.

00:00:15
Patients are experiencing headaches and nausea.
```

We retain both languages rather than replacing the original transcript.

Output:

* `original_transcript.txt`

* `english_transcript.txt`

### Stage 5 — Subtitle extraction and processing

Technology: FFmpeg + GPT-4o + Python.

There are two cases:

Case A: Embedded subtitle track

If the video contains a separate subtitle stream, FFmpeg extracts it.

Case B: Burned-in subtitles

If Japanese subtitles are permanently displayed on the video:

* OpenCV provides the relevant frames.

* GPT-4o Vision reads the visible Japanese text.

* We preserve its timestamp.

* GPT-4o translates it into English.

* Python generates subtitle files.

Outputs:

* `original_subtitles.srt`

* `english_subtitles.srt`

We should compare the extracted burned-in subtitles with the speech transcript. They may not always be identical.

Model: GPT-4o Vision.

This is one of the most important parts of our platform.

We send selected video frames to GPT-4o in batches.

For our proposed initial design:

* 3,600 frames extracted locally.

* Approximately 250 selected for AI analysis.

* 10 images per visual request.

* Approximately 25 visual-analysis requests.

GPT-4o analyses the frames for:

| Category            | What it extracts                          |
| ------------------- | ----------------------------------------- |
| OCR                 | Japanese text displayed in images         |
| Subtitles           | Burned-in Japanese subtitles              |
| Products            | Product and medicine names                |
| Brands              | Logos and brand names                     |
| Medical information | Symptoms, risks and adverse effects       |
| Charts              | Titles, labels, values and trends         |
| Chats               | Messages and patient experiences          |
| Other visuals       | Screenshots, packaging, labels and claims |

For example, a slide might display:

* Medicine: Product A

* Claimed benefit: Reduces symptoms

* Reported risk: Nausea

* Other reported effect: Headache

The speaker may mention only nausea, while the slide also displays headache.

Our system must retain both findings.

Accuracy consideration: Japanese text and small text can be challenging for vision models. Important text should be cropped and enlarged for inspection. GPT-4o can make mistakes, so unreadable content should be marked rather than guessed. Microsoft Learn +1

### Stage 7 — Entity and information extraction

Model: GPT-4o.

Now we consolidate the important entities from both audio and visual evidence.

Example:

```json
{
  "products": [
    {
      "name": "Product A",
      "source": "visual",
      "timestamp": "00:00:12"
    }
  ],
  "medical_entities": [
    {
      "name": "Headache",
      "category": "adverse_effect",
      "source": "visual"
    },
    {
      "name": "Nausea",
      "category": "adverse_effect",
      "source": "audio"
    }
  ]
}
```

We extract:

* Product names.

* Medicine names.

* Brand names.

* Symptoms.

* Adverse events.

* Benefits and claims.

* Risks and warnings.

We should distinguish explicitly displayed information from model-inferred information.

### Stage 8 — Evidence layer

Technology: GPT-4o + Python + Pydantic + Azure SQL + Blob Storage.

This is the central part of our architecture.

Instead of generating summaries immediately, we first create structured evidence records.

Every finding should contain:

| Field           | Purpose                             |
| --------------- | ----------------------------------- |
| Evidence ID     | Unique identification               |
| Video ID        | Original video reference            |
| Timestamp       | When it appeared                    |
| Source          | Audio, subtitle or visual           |
| Category        | Product, risk, symptom, claim, etc. |
| Original text   | Japanese finding                    |
| English text    | English translation                 |
| Confidence      | Extraction confidence               |
| Frame reference | Relevant image, if applicable       |

Example:

```json
{
  "evidence_id": "EV_001",
  "video_id": "VID_001",
  "timestamp": "00:00:15",
  "source": "visual",
  "category": "adverse_effect",
  "original_text": "頭痛",
  "english_text": "Headache",
  "confidence": 0.94,
  "frame_reference": "frame_015.jpg"
}
```

Confidence here means confidence in extracting or interpreting the finding, not whether the medical claim is scientifically true.

All records are stored in Azure SQL, while original files and extracted assets are stored in Blob Storage.

### Stage 9 — Evidence comparison and discrepancy detection

Model: GPT-4o.

Now we compare three independent sources:

* What the speaker says.

* What the subtitles display.

* What the images, slides and chats display.

Example:

| Information | Audio | Subtitles | Visuals |
| ----------- | ----- | --------- | ------- |
| Nausea      | Yes   | Yes       | Yes     |
| Headache    | No    | No        | Yes     |
| Dizziness   | Yes   | Yes       | No      |

Our system identifies:

* Information appearing in all sources.

* Information appearing only in audio.

* Information appearing only visually.

* Differences between spoken and displayed content.

* Potential contradictions requiring review.

We do not automatically call something false just because it differs between sources.

### Stage 10 — Final summarization

Model: GPT-4o.

Once evidence is collected and reconciled, GPT-4o generates three outputs.

1\. Video summary

Audio-based

Summarises what the speaker discusses.

2\. Visual summary

Visual-based

Summarises products, screenshots, text, charts, symptoms and other displayed information.

3\. Executive summary

Combined intelligence

Combines audio and visual findings, highlights important claims, discrepancies and potential risks.

Every important finding should link back to its evidence ID and timestamp.

The user performs only one action: clicks Analyse.

The backend handles the internal workflow.

```text
      +---- Frame Extraction
                 |

                 |
                 v

                 |

                 |

                 |

                 |
```

For production, I recommend a background job worker so that a long-running analysis does not keep the initial HTTP request open. FastAPI manages the API, while the worker executes the processing stages and updates the job status.
